# 설계 세부

이 문서는 [PLAN.md](../PLAN.md)에서 내린 결정을 실제로 지키기 위한 규칙과 그 근거를 적는다. 처음 읽는 사람은 PLAN.md부터 읽는 것이 좋다. 파일 단위로 무엇을 만드는지는 [implementation-plan.md](implementation-plan.md)에 있다.

## 실행

### loadtest 단계의 세부

- **입력 확인에서 멈추는 경우**: 계획에는 흐름별 도착률, 태스크 대수, 필요한 회원 수, 최대 VU, 예상 시계열 수, 예상 시간이 들어간다. 시나리오마다 상한을 둔다(예: smoke는 초당 20건 이하). 다음 경우에는 실행하지 않고 멈춘다.
  - 상한을 넘었을 때
  - `runners`를 계산한 대수보다 적게 넣었을 때
  - 필요한 회원이 시험 회원 수(설정값)보다 많을 때
  - 시계열이 2만 개를 넘을 때
  - `open_at`까지 남은 시간이 준비 구간을 돌리기에 모자랄 때
  - spike인데 `prep_product_id`를 따로 넣지 않았을 때. 같은 상품을 쓰면 준비 구간이 `SALE_NOT_OPEN`으로 막힌다
  - 태스크 대수가 `runner.max_tasks`를 넘을 때. Fargate vCPU 할당량은 운영 서비스와 같이 쓰므로, 할당량에서 운영 사용분을 뺀 값을 설정에 적어 둔다
- 계산한 계획은 실행 요약에 표로 적는다. 계획 계산에는 컨트롤러와 같은 코드를 쓴다.
- **사전 점검**: 공개 상품 API로 시험 상품이 있는지, 판매 중인지, 옵션이 있는지 확인한다. 러너가 직접 확인할 수 없는 항목은 승인자가 승인하기 전에 runbook의 점검표로 확인한다.
  - 회차 일정(`opensAt`, `closesAt`)은 관리자 API에만 있어서 러너가 볼 수 없다.
  - 러너는 Cognito 뒤에 있는 Grafana에도 접근할 수 없으므로, 지금 울리는 경보가 있는지 볼 수 없다.
  - 러너는 DB도 볼 수 없으므로, 시험 회원은 준비 SQL을 돌렸다는 runbook의 기록으로 확인한다.
  - Grafana 경보 사일런스도 처음에는 사람이 건다. 대상은 `nova-slo` 그룹(`slo-*`, `traffic-drop`, `latency-vs-baseline`), `nova-http-p99`, `nova-http-5xx`이고, 끝 시각은 예상 종료 시각에 15분을 더한 시각이다.
- **컨트롤러 실행**: 시험 ID와 계획을 넘겨 컨트롤러 태스크를 띄우고, 끝날 때까지 기다린다. 컨트롤러가 결과를 남기지 못하고 끝나면(태스크 실패, 강제 종료) "판정 불가"로 본다.
- 사전 점검부터 뒷정리까지는 한 작업(job) 안의 단계로 둔다. environment에 승인자를 두면, 그 environment를 쓰는 작업마다 따로 승인을 기다리기 때문이다. 결과 정리와 뒷정리를 다른 작업으로 나누면 시험이 끝난 뒤에 다시 승인해야 하고, 그동안 뒷정리가 멈춰 있게 된다.
- 판정 결과가 합격일 때만 워크플로가 성공한다. stress만 예외이다(아래 "시나리오별 세부"의 stress).
- 같은 시간에는 시험을 하나만 돌린다(`concurrency`). 진행 중인 시험을 취소하지는 않는다.
- **시험 ID**는 `lt-<UTC yyyymmddThhmm>-<run_number>` 형식이다(예: `lt-20261017t0630-12`). 소문자, 숫자, `-`만 쓴다. 이 값을 RunTask의 `startedBy`(36자 이하, 영문·숫자·`-`·`_`), k6의 `test_id` 태그, User-Agent, S3 경로에 그대로 쓰기 때문에, 모든 곳에서 허용되는 글자만 골랐다.
- AWS에는 OIDC로 맡는 역할로 접근한다. 세션은 1시간인데, 컨트롤러를 기다리는 단계 하나가 몇 시간씩 걸릴 수 있다. 단계 안에서는 `configure-aws-credentials`를 다시 부를 수 없으므로, 기다리는 Go 명령이 50분마다 Actions OIDC 토큰을 새로 받아 `AssumeRoleWithWebIdentity`로 세션을 바꾼다.
- **OIDC 신뢰 조건**: 작업이 `loadtest` environment를 쓰면 OIDC 토큰의 `sub`가 `repo:<저장소>:environment:loadtest`로 바뀐다. 이 저장소는 immutable subject 형식이라 `<저장소>`가 `Grandis-2@<ID>/nova-loadtest@<ID>`이다([설정과 비밀 값](configuration.md#oidc-신뢰-조건)). 그래서 브랜치 조건(`ref:refs/heads/main`)만으로는 역할을 맡을 수 없다.
  - 시험 실행 역할은 environment 값을 신뢰한다. main에서만 돌게 하는 제한은 environment의 배포 브랜치 규칙이 맡는다.
  - `build.yml`, `stop.yml`, 그리고 `loadtest.yml`의 입력 확인 작업은 environment 없이 main 조건으로 빌드 역할을 맡는다.
- 태스크는 `latest` 이미지로 돈다. RunTask로는 이미지를 바꿀 수 없기 때문이다. 대신 결과에 이미지 다이제스트와 커밋을 남긴다. 시험 중에 `latest`가 바뀌지 않게 하는 방법은 아래 "인프라 값"에 있다.
- 이미지는 x86_64(`linux/amd64`)로 빌드한다. 작업 정의의 `runtimePlatform`이 X86_64이기 때문이다. GitHub 러너도 x86_64라서 에뮬레이션 없이 빌드할 수 있고, Go 실행 파일은 `GOARCH=amd64`로 만든다. 태스크당 처리량도 이 기준으로 실측한다.
- RunTask에는 `tags`를 넘기지 않고 `startedBy=<시험 ID>`만 쓴다. 태스크를 찾을 때는 `ListTasks(startedBy)`로 고르고, k6인지 컨트롤러인지는 `DescribeTasks`가 돌려주는 작업 정의로 구분한다.
- GitHub Actions의 작업 하나는 최대 6시간까지 돈다. 그래서 soak 시험은 4시간 안으로 잡는다. 더 긴 시험이나 정기 실행이 필요해지면 그때 Step Functions로 옮긴다. 컨트롤러가 이미 태스크로 돌기 때문에 트리거만 바꾸면 된다.

## k6 분배

### 부하 나누기

- k6의 실행 구간(execution segment) 기능을 쓴다. 태스크 i(0부터 N-1까지)는 `--execution-segment "i/N:(i+1)/N"`을 받고, 모든 태스크가 같은 `--execution-segment-sequence`를 받는다.
- 도착률 기반 실행기(`constant-arrival-rate`, `ramping-arrival-rate`)는 이 구간에 따라 N등분된다. 예를 들어 초당 500건을 5대로 나누면 태스크마다 초당 100건을 보낸다. `preAllocatedVUs`와 `maxVUs`도 같이 나뉜다.

### 동시 시작

- k6에는 시작 시각을 정하는 옵션이 없다. 그래서 k6 이미지의 시작 프로그램(`k6-runner`, Go)이 토큰을 받은 뒤 시각 T까지 기다렸다가 `k6 run`을 실행한다. 이 프로그램을 셸 스크립트가 아닌 Go로 만들면, 기반 이미지에 셸이나 AWS CLI가 없어도 되고 S3 서명과 신호 전달을 한곳에서 처리할 수 있다.
- Fargate 태스크는 뜨는 데 걸리는 시간이 30~60초씩 차이가 난다. 그래서 컨트롤러가 시작 시각 T(지금부터 약 2분 뒤)를 정해 모든 태스크에 넘긴다.
- Fargate는 AWS Time Sync로 시계를 맞추므로, 태스크 사이의 시각 오차는 1초 안이다.
- 시각 T까지 뜨지 못한 태스크가 있으면 컨트롤러가 시험을 취소한다. 일부 태스크만 시작하면 부하가 계획보다 적게 나가기 때문이다.

### 멈추기

- 태스크를 멈추면 `k6-runner`가 SIGTERM을 k6에 넘긴다. k6는 실행을 끊고, 남은 지표를 보내고, 요약을 쓴 뒤 종료 코드 105로 끝난다. 이 작업에 필요한 시간을 확보하려고 작업 정의의 `stopTimeout`을 120초로 둔다.
- 끝난 이유는 종료 코드로 구분한다: 0은 정상, 99는 임계치 실패, 105는 외부에서 중지, 107은 스크립트 오류, 108은 스크립트가 스스로 중단한 경우이다.

### 태스크별 요약

- k6는 `handleSummary`로 요약을 파일로 쓰고, `k6-runner`가 종료 코드와 함께 S3의 `results/<시험 ID>/k6-<i>.json`에 올린다. 태스크를 멈출 때도 `stopTimeout` 안에 올린다.
- 요약에 들어 있는 백분위는 태스크 하나의 값이므로 합치지 않는다. 판정은 Mimir로 한다. 요약에서는 임계치 결과, `check` 성공률, 요청 수와 실패 수, 밀린 반복 수를 본다. 요청 수와 실패 수는 태스크끼리 더할 수 있으므로, 지표가 끊겨 판정 불가가 된 시험에서도 실제로 보낸 양은 알 수 있다.
- 결과(`results/`)는 180일 동안 보관하므로, 요약에 토큰이나 부하 시험 헤더가 들어가면 안 된다. `setup()`의 반환값이 요약에 그대로 들어가므로, 이 반환값에는 상품 옵션 ID 같은 공개 값만 둔다.

### User-Agent

- 모든 요청의 User-Agent를 `nova-loadtest/<시험 ID>`로 고정한다(k6의 `userAgent` 옵션). 흐름 코드에서는 이 값을 바꾸지 않는다. 이렇게 하면 CloudFront, ALB, 서비스의 로그에서 시험 요청을 골라낼 수 있고, 어느 시험의 요청인지도 알 수 있다.
- User-Agent는 누구나 흉내 낼 수 있다. 그래서 WAF 예외는 User-Agent가 아니라 부하 시험 헤더로만 건다.

### 회원 나누기

- 토큰 발급기는 태스크와 회원 풀마다 토큰 파일을 따로 만든다(`{a,b,c}-<i>.json`). 그래서 태스크끼리 회원이 겹치지 않고, 태스크가 큰 파일을 잘라 읽을 필요도 없다.
- 태스크 안에서는 흐름마다 회원 풀을 나누고, 반복 번호에 따라 회원을 차례로 고른다(아래 "회원 풀 나누기"). 회원 한 명이 대기열부터 예약까지 한 흐름을 처음부터 끝까지 맡는다.
- 토큰은 `SharedArray`로 한 번만 읽고, 모든 VU가 같이 쓴다.

### 실행기 크기

- 태스크 하나는 Fargate 4 vCPU, 8GB로 둔다. 태스크 하나가 초당 몇 건까지 보낼 수 있는지는 공식 수치가 없다. smoke와 load에서 실측하고, 그때까지는 태스크당 초당 1,000건으로 계산한다.
- 대기열에서 기다리는 회원은 기다리는 동안 VU를 하나씩 계속 차지한다. 그래서 필요한 VU 수는 초당 요청 수보다 "동시에 기다리는 회원 수"에 따라 정해진다. VU 하나에 메모리 1~5MB를 잡고, 이 값을 태스크 대수에 반영한다.
- 목표 부하보다 30% 이상 여유를 두고 띄운다. 실행기 CPU가 80%를 넘으면 실행기가 병목이 된 것이므로, 결과를 버리고 대수를 늘려 다시 시험한다.
- 실행기 CPU는 k6 지표에 없으므로, 시험 클러스터의 Container Insights를 켜서 본다. Grafana에 CloudWatch 데이터 소스가 있어서 k6 대시보드에 함께 놓을 수 있다. 평소에는 태스크가 0대라서 비용이 거의 들지 않는다.
- `discardResponseBodies`를 켜고, 본문이 필요한 요청(대기열, 접수, 예약 목록)만 본문을 받는다. 파일 핸들 상한(`nofile`)도 올린다.

### 결과 합치기와 판정

- 태스크마다 계산한 백분위를 평균하면 틀린 값이 나온다. 그래서 응답 시간을 히스토그램으로 Mimir에 보내고, Mimir가 모든 태스크의 값을 합쳐 계산한다.
- k6의 OTel 출력은 Trend 지표를 explicit bucket 히스토그램(누적)으로 보낸다. 버킷 경계는 0, 5, 10, 25, 50, 75, 100, 250, 500, 750, 1000, 2500, 5000, 7500, 10000ms로 고정되어 있고, k6에서 바꿀 수 없다. 게이트웨이는 이 값을 Mimir의 OTLP 입구로 그대로 넘긴다.
- k6의 임계치(threshold)는 태스크마다 따로 판단한다. 그래서 임계치는 합격 여부를 정하는 데 쓰지 않고, 태스크 안의 안전장치로만 쓴다.
  - 모든 k6 태스크는 오류율 임계치에 `abortOnFail`을 건다: `http_req_failed` 비율 < `abort_error_rate`, `delayAbortEval: 1m`. 값은 컨트롤러의 중단 기준과 같다.
  - 이 안전장치는 Mimir와 상관없이 동작한다. 지표 경로가 끊기거나 컨트롤러가 죽어도 태스크가 스스로 멈춘다.
  - 다만 k6의 임계치는 최근 1분의 비율이 아니라 시험을 시작한 뒤의 누적 비율로 판단하므로, 오래 정상으로 돈 뒤에 오류가 나면 늦게 걸린다. 예를 들어 30분 동안 정상으로 돈 뒤 모든 요청이 실패하면 누적 비율이 5%를 넘기까지 약 1.6분이 걸리고, soak에서 4시간이 지난 뒤라면 약 13분이 걸린다. 그래서 1분 기준의 빠른 중단은 컨트롤러가 맡고, k6 임계치는 컨트롤러가 없을 때를 대비한 보조 장치로 둔다. 컨트롤러가 죽으면 워크플로의 뒷정리가 k6 태스크를 멈춘다.
  - 정상 응답을 실패로 세지 않도록, 요청마다 `responseCallback`으로 기대하는 상태 코드를 정한다. `setResponseCallback`은 전역에 하나만 둘 수 있어서 흐름별로 다르게 정할 수 없기 때문이다. 예를 들어 대기열 요청은 200과 202가 정상이다. 이렇게 하지 않으면 4xx 응답이 모두 실패로 잡혀 임계치가 잘못 걸린다. 콜백은 상태 코드만 보므로, 409처럼 오류 코드로 구분해야 하는 응답은 `check`와 오류 코드별 카운터로 따로 센다.
  - 태스크 하나가 시험 도중 임계치에 걸려 멈추면(종료 코드 99), 남은 태스크만으로는 계획한 부하를 낼 수 없다. 그래서 컨트롤러가 나머지 태스크를 모두 멈추고 시험을 "중단"으로 끝낸다. 계획한 끝 시각에 99로 끝난 태스크는 중단으로 보지 않고, 판정은 Mimir로 한다.
- 전체 합격 여부는 컨트롤러가 Mimir로 정한다. 기준은 운영 SLO와 같으며, 응답 시간 p95 0.5초와 5xx 비율 0.1%이다. 판정 결과 다섯 가지와 정하는 순서는 [PLAN.md "판정"](../PLAN.md#판정)에 있다.
- 컨트롤러는 k6의 `http_req_failed`와 같은 정의로 오류율을 계산한다(`expected_response="false"`인 요청의 비율). 그래서 두 장치가 같은 요청을 실패로 센다.
- **판정 불가**: 시험 중에 어느 태스크(`service.instance.id`)의 지표라도 1분 넘게 들어오지 않으면, 지표가 끊긴 것으로 본다. 태스크가 RUNNING 상태여도 마찬가지이다.
  - 태스크가 살아 있는지는 `vus` 지표로 본다. 이 지표는 요청이 없는 구간에도 매초 나온다.
  - 지표가 끊기면 컨트롤러가 감시를 할 수 없으므로, 모든 태스크를 멈추고 "판정 불가"로 끝낸다. Mimir를 1분 넘게 조회하지 못할 때도 같다.
  - 시험이 끝난 뒤 판정할 때도 태스크마다 시험 구간 전체의 지표가 있는지 먼저 본다. 빠진 구간이 있으면 수치를 내지 않고 "판정 불가"로 둔다.
- p95 판정은 "0.5초 안에 끝난 요청의 비율이 95% 이상인가"로 한다. 500ms가 버킷 경계이므로 이 비율은 근사 없이 정확하게 구할 수 있다. `histogram_quantile`로 구한 p95와 p99는 버킷 폭이 넓어서(250~500ms, 500~750ms) 참고값으로만 보여 준다.
- k6의 리소스 속성은 `service.namespace=loadtest`로 둔다. `nova`로 두면 운영 SLO의 기록 규칙에 시험 지표가 섞인다.

## 흐름과 회원 풀

흐름과 비율은 breakscale의 클라이언트 구성을 따른다. API 경로와 요청 형식은 be `contracts/` 문서가 아니라 be main 브랜치의 컨트롤러와 DTO 코드를 직접 보고 맞춘다(마지막 대조: `4d5863cb`, 2026-10-19).

| 흐름 | 요청 | 회원 | 평시 초당 흐름 수 |
|---|---|---|---|
| 진입과 접수 | `POST /api/v1/preorders/queue?productId=`를 보낸다. 바로 입장하면 200과 `ADMITTED`, 줄에 서면 202와 `WAITING`(`queueToken`, 헤더 `Retry-After`)이 온다. 202면 `Retry-After`에 적힌 초마다 `Queue-Token` 헤더를 실어 `GET`으로 확인한다. 확인 응답에 새 `queueToken`이 오면(만료가 가까울 때 바뀐다) 그 값으로 바꾼다. `ADMITTED`가 되면 `admissionTicket`을 받고, `POST /api/v1/preorders?productId=`에 `Idempotency-Key`(8~64자), `X-Admission-Ticket`, 본문 `{productId, optionId}`를 보낸다. 성공은 202이다 | 풀 A | 5 |
| 내 예약 조회 | `GET /api/v1/preorders`, `/active`, `/{preorderId}` | 풀 B | 10 |
| 예약 취소 | `GET /api/v1/preorders?productId=<준비 상품>`으로 예약을 찾고 `POST /api/v1/preorders/{preorderId}/cancel`을 보낸다. 본문은 선택(`{reason}`)이고 `Idempotency-Key`는 받지 않는다. 성공은 202이다 | 풀 C | 1 |
| 주문과 결제 시도 | `GET /api/v1/preorders?productId=<준비 상품>&status=REGISTERED`로 등록이 끝난 예약을 찾는다. `POST /api/v1/orders`(본문 `source=PREORDER`, `preorderId`, `shipTo{name, phone, postalCode, line1, line2}`)를 보낸다. 새로 만들면 201, 같은 예약의 주문이 이미 있으면 200과 그 주문이 온다. `PREORDER` 주문은 `Idempotency-Key`를 받지 않는다. 이어서 본문 없이 `POST /api/v1/orders/{orderId}/payment-attempts`를 보낸다(201). 결제 시도 생성은 결제사(토스)를 호출하지 않고, preorder에 결제 가능 여부를 다시 묻고 payment에 대기 중인 거래를 만든다. 결제 승인은 보내지 않는다 | 풀 B | 5 |
| 상품 조회 | `GET /api/v1/products`, `/{productId}`, `GET /api/v1/categories`. 토큰이 필요 없다 | 없음 | 80 |

- 결제나 취소할 예약을 찾을 때는 `/active`를 쓰지 않는다. `/active`에는 상품 필터가 없어서, 회원을 다시 쓰면 지난 시험 상품의 예약까지 나오고 그 예약을 결제하거나 취소하게 된다. 그래서 목록 API의 `productId`로 이번 준비 상품의 예약만 고른다. `/active`는 조회 흐름의 부하로만 부른다.
- 평시 비율은 breakscale `01-평시`를 따른다. breakscale README의 "평시 트래픽 비율"(폴링 300, 상품 200 …)은 02, 03 시나리오의 배경 트래픽이므로 평시로 쓰지 않는다.
- 대기열 확인 요청에는 도착률을 따로 정하지 않는다. 진입한 회원이 서버가 알려 준 간격대로 확인하므로, 확인 요청 수는 기다리는 인원에 따라 저절로 정해진다. breakscale이 예측한 확인 요청 수와는 결과로 비교한다.
- productId는 소문자 UUID여야 한다. 대문자가 섞이면 400 응답이 온다.
- 접수 본문의 `optionId`는 공개 상품 상세(`GET /api/v1/products/{productId}`)의 `variants[].variantId`와 같은 값이다(catalog의 옵션 ID). k6는 `setup()`에서 상품 상세를 읽어 판매 중인 variant의 ID를 쓴다.
- 모든 응답은 `{success, data, error{code, message, details}, timestamp, traceId}` 봉투로 온다. 오류는 `error.code`로 구분한다.
- 대기 응답에 `paused: true`가 오면 줄이 멈춘 것이다. 순서는 그대로이므로 확인을 계속해야 자리가 남는다.
- 주문은 예약이 `REGISTERED`가 된 뒤에 만들 수 있다. 그 전이면 409 `PREORDER_NOT_PAYABLE`이 온다.
- 주문 배송지는 형식 검사 없이 길이만 본다(이름 50자, 전화 20자, 우편번호 10자, 주소 200자, 상세 주소는 선택). k6는 회원 번호로 자연스러운 한글 이름, 전화번호, 주소를 만들어 보낸다(`k6/lib/fake.js`).
- 로그인과 토큰 재발급은 넣지 않는다. 직접 발급한 토큰에는 세션 기록이 없어서 재발급이 되지 않는다. 로그인 부하를 재야 한다면 be에 시험 전용 로그인을 요청한다.
- 서버가 느려져도 보내는 양이 줄지 않도록 도착률 기반 실행기를 쓴다.
- 모든 요청에 `tags.name`을 경로 템플릿으로 붙인다(예: `/api/v1/products/{id}`). 메서드는 `method` 태그가 따로 있으므로 넣지 않고, 쿼리 문자열(`?productId=`)도 넣지 않는다. k6는 `name`이 없으면 URL 원문을 넣는데, 그러면 ID마다 시계열이 생겨 끝없이 늘어난다. 시계열 수를 지키는 것은 이 태그이고, 게이트웨이 필터는 실수했을 때를 대비한 안전망일 뿐이다.
- be의 기존 시험 스크립트(`waitingroom/load-test/entry-spike.js`, `preorder/load-test/accept-spike.js`)를 요청 형식의 참고 자료로 쓴다.

### 회원 풀 나누기

- **풀 A(진입과 접수)**: 시험 상품에 처음 들어오는 회원이다. 대기열은 회원마다 자리를 하나만 주고, 예약은 상품 하나에 회원 한 명당 1건만 가능하다. 그래서 한 시험에서 회원 한 명은 한 번만 쓴다.
- **풀 B(조회, 결제)**: `prep_product_id`에 이미 예약을 가진 회원이다. 조회와 결제 시도는 같은 회원이 되풀이해도 되므로 풀의 크기가 작아도 된다(예: 1,000명). 주문은 같은 예약이면 기존 주문을 다시 쓰고, 결제 시도는 부를 때마다 새로 생긴다.
- **풀 C(취소)**: 풀 B와 같은 방식으로 준비하지만 취소에만 쓴다. 취소한 회원은 예약이 없어지므로 조회와 결제 풀에 섞지 않는다. 크기는 취소 도착률에 시간을 곱한 값이다.
- **준비 구간**: 본 시험 앞에서 풀 B와 C가 낮은 속도(초당 100건 이하)로 진입과 접수를 마친다. 그 뒤 worker가 등록을 끝내 예약이 `REGISTERED`가 될 때까지 기다렸다가(약 2분) 본 시험을 시작한다.
- **spike**: 판매가 열리는 순간을 재현하려면, 진입할 상품의 회차가 본 시험 시작 시각(`open_at`)에 열려야 한다. 회차가 열리기 전에는 진입이 `SALE_NOT_OPEN`으로 막히므로, 준비 구간을 같은 상품에서 돌릴 수 없다. 그래서 spike에서는 풀 B와 C를 `prep_product_id`(미리 열어 둔 다른 시험 상품)에 준비한다.
- 시험마다 새 시험 상품을 쓰므로, 같은 시험 회원을 다음 시험에 다시 쓸 수 있다. 다만 정리하지 않으면 회원마다 지난 시험의 예약이 쌓여 조회 응답이 커진다. 시험 결과끼리 비교하려면 정리한 뒤에 다음 시험을 한다.
- 등록된 예약을 24시간 안에 결제하지 않으면 서버가 자동으로 취소한다(결제 기한). 그래서 정리하지 않은 예약도 하루 뒤에 취소되고, 이때 worker와 Mock에 취소 요청이 간다.
- 시험 회원은 10만 명을 넣어 두고 계속 쓰는 방식을 제안한다. 회원 행은 크기가 작아 부담이 적다. 토큰은 시험마다 필요한 범위만 발급한다.
- 진입이 입장 속도(초당 150건)보다 빠르게 계속 들어오면 기다리는 회원이 쌓이고, VU도 그만큼 늘어난다. 예를 들어 breakscale 03(진입 초당 500건)을 5분 동안 유지하면 약 10만 명이 기다리게 된다. 이런 시나리오는 유지 시간을 짧게 잡는다. 최대 VU는 입력 확인 단계에서 계산하고 상한을 둔다.

## 시나리오별 세부

부하의 단위는 흐름 시작 수(초당 반복 수)이다. 입력 `peak_rps`도 흐름 시작 수의 합계이다. 흐름 하나가 요청을 여러 건 보내므로(조회 3건, 결제 3건, 진입은 기다리는 동안 계속) 실제 초당 요청 수는 이보다 많다. 그래서 계획을 계산할 때는 흐름별 요청 수로 예상 요청 수를 따로 구하고, 태스크 대수와 WAF 계산에는 이 값을 쓴다.

**smoke**

- smoke는 두 번에 나눠 돌린다. 먼저 토큰, 회원, 시험 상품 없이 상품 조회만으로 이미지, 실행 경로, 지표 경로를 확인한다(C-2). 그다음에 다섯 흐름을 모두 돌린다(C-4).
- smoke는 WAF 예외가 없어도 돌 수 있어야 한다. 첫 smoke는 WAF 예외(I-5)를 적용하기 전에 돌기 때문이다. k6는 부하 시험 헤더를 늘 붙이지만, 예외가 적용되기 전에는 헤더가 있어도 요청 제한을 받는다. k6 1대가 IP 하나를 쓰므로, 요청 수가 IP당 5분 3,000회(대기열 경로는 제외) 안에 들어야 한다.
  - 흐름당 요청 수는 상품 조회 3건, 예약 조회 3건, 결제 3건, 취소 2건, 진입과 접수 1건(대기열 확인은 제외 경로)이다. 평시 비율로 섞으면 흐름 하나에 평균 약 2.9건이므로, 초당 5흐름이면 초당 약 14.5건이고 본 시험 2분 동안 약 1,750건이다.
  - 준비 구간(풀 B 50명과 풀 C 몇 명의 접수와 조회, 100건 안팎)을 더하면 5분 창에 약 1,850건이다. 상한 2,400건 안에 들어가지만 여유가 크지 않으므로, smoke의 부하나 시간을 늘리려면 이 계산을 다시 해야 한다.
- 입력 확인 단계는 WAF 예외가 없는 시나리오에서 태스크(IP)당 5분 요청 수를 계산하고, 2,400건(20% 여유)을 넘으면 멈춘다.

**load**

- 평시 비율에 배수를 곱한다. 이때 진입도 같이 곱해지는데, 진입이 입장 속도(150/초)를 넘으면 기다리는 회원이 쌓여 VU가 끝없이 늘어난다. 그래서 입력 확인 단계가 진입 시작 수를 입장 속도의 80%(120/초) 아래로 제한한다. 그보다 큰 배수가 필요하면 진입만 120/초에 묶어 둔다.
- 판정에는 유지 구간만 쓴다. 부하를 올리는 처음 1분은 뺀다.

**spike**

| 구간 | 시간 | 하는 일 |
|---|---|---|
| 준비 | `open_at` 전 | `prep_product_id`에서 풀 B와 C를 진입·접수시키고, 예약이 `REGISTERED`가 될 때까지 기다린다 |
| 배경 | 본 시험 시작(`open_at`)부터 시험 끝까지. 등록 대기 중에 돌리면 주문과 취소가 아직 등록되지 않은 예약을 찾는다 | breakscale 02의 배경 트래픽에서 로그인을 뺀 부하를 보낸다: 상품 200, 예약 조회 30, 결제 10, 취소 1. 대기열 확인 요청은 따로 정하지 않는다 |
| 몰림 | `open_at` + 1초부터 10초 동안 | `product_id`에 초당 500건씩, 모두 5,000명(풀 A)이 진입한다 |
| 관찰 | 몰림 뒤 10분 | 진입은 평시 수준(5/초)으로 돌아간다. 대기열이 비고, 등록 큐와 `preorder-events`가 빠지는 과정을 본다 |

- 몰림을 `open_at` + 1초에 시작하는 이유: 서버와 k6의 시계가 1초 안에서 어긋날 수 있기 때문이다. 회차가 열리기 전에 들어간 진입은 `SALE_NOT_OPEN`이 되어 실패로 섞인다.
- 기다리는 5,000명이 VU를 하나씩 차지한다. 서버는 예상 대기 시간에 따라 확인 간격을 1, 3, 10, 30초(흔들림 20%)로 알려 준다. 입장이 초당 150명이므로 마지막 회원은 약 33초를 기다린다. 확인 요청은 몰림 직후에 초당 1,000~2,000건까지 올라가며, 계획 계산은 이 값으로 태스크 대수를 정한다.
- k6가 바빠서 확인 요청이 늦어지면 서버는 그 회원을 이탈자로 보고 줄에서 뺀다. 그러면 서버 문제가 아니라 실행기 문제로 시험이 실패한다. 이런 경우는 `k6-runner`의 요약과 실행기 CPU를 보고 구분한다.
- 진입 흐름의 `gracefulStop`은 3분으로 둔다. 기본값인 30초로 두면 시험이 끝날 때 줄에 서 있던 회원이 잘려서 접수까지 가지 못한다.
- breakscale 03(진입 초당 500건이 계속되는 경우)은 기본 시나리오에 넣지 않는다. 기다리는 회원이 초당 350명씩 늘어나 1분이면 2만 명이 되고, VU 메모리만 100GB가 넘는다(VU당 5MB). 회원도 1분에 3만 명이 필요하다. 이 시나리오는 VU 메모리를 실측한 뒤(C-5) 1분 이하로 따로 계획한다.

**rush**

spike는 몰린 회원이 접수에서 끝나고, 결제는 준비해 둔 다른 회원(풀 B)이 따로 한다. rush는 판매 오픈에 몰린 회원 한 명이 접수 뒤에 등록 알림을 받아 결제 시도까지 이어 가는 흐름을 재현한다. 등록 큐가 밀리면 결제가 늦게, 그리고 한꺼번에 들어오는 연쇄를 보려는 것이다.

| 단계 | 요청 | 하는 일 |
|---|---|---|
| 오픈 순간 | `GET /api/v1/products/{id}` | 상품 상세를 새로 고친다 |
| 진입, 줄, 접수 | spike의 진입 흐름과 같다 | 접수 응답의 `preorderId`(예약의 공개 토큰)를 기억한다 |
| 등록 알림 기다리기 | `GET /api/v1/notifications/unread-count`를 10초마다 | 처음 본 수보다 늘면 `GET /api/v1/notifications`에서 이 예약의 `PREORDER_REGISTERED`(`target.id`가 `preorderId`)를 찾는다. 8분 안에 오지 않으면 `notify_timeout`으로 세고 결제를 건너뛴다 |
| 결제 | `GET /api/v1/preorders/{id}`, `POST /api/v1/orders`, `POST .../payment-attempts` | 알림을 눌러 예약 상세를 열고 결제하기를 누른다. 결제 승인은 보내지 않는다 |

- 바로 결제하는 회원은 접수한 회원의 50%(`scenarios.rush.rush.pay_ratio`)다. 나머지는 접수만 하고 떠난다(24시간 안에 나중에 결제한다고 본다). 회원 번호로 고르므로 같은 회원은 늘 같은 쪽이다.
- 화면은 안 읽은 알림 수를 실시간 연결(SSE, `GET /api/v1/notifications/stream`)로 받는다. k6에는 SSE가 없어서 안 읽은 수 조회로 흉내 낸다. 그래서 member에는 실제보다 HTTP 요청이 많이 가고, SSE 연결 자체가 주는 부하는 보지 않는다. 결제할 2,500명이 함께 기다리면 member(1대)에 초당 250건이 간다. 간격을 더 줄이면 실제에 없는 조회가 member를 바쁘게 해 알림 저장까지 늦출 수 있어 10초로 둔다. 그래서 `accept_to_notified`는 10초 단위로만 정확하다.
- 컨트롤러는 RunTask 크기 상한 때문에 k6에 계획을 줄여서 넘긴다. 결제 비율과 `open_at`도 그 안에 넣는다(빠지면 k6가 결제 비율 0으로 돌아 아무도 결제하지 않는다).
- 알림 목록을 받지 못하면 다음 확인에서 다시 연다. 목록은 첫 쪽(20건)만 본다. 시험 중에 회원 한 명에게 새로 오는 알림은 이 예약의 등록 알림뿐이라 늘 맨 앞에 있다.
- 안 읽은 알림이 있으면 목록을 열어 이 예약의 알림인지 보고, 그 뒤로는 수가 늘었을 때만 다시 연다. 지난 시험의 알림이 안 읽은 채로 남아 있어도 목록을 매번 열지 않기 위해서다. 접수 직후의 수를 기준으로 삼지 않는 까닭은, 그 사이에 알림이 이미 왔으면 수가 더 늘지 않아 끝내 찾지 못하기 때문이다.
- 준비 구간이 없다. 배경은 회원이 필요 없는 상품 조회(초당 200)만 둔다. 그래서 상품 하나(`product_id`)와 풀 A만 쓴다. `prep_product_id`와 `flows`는 거절한다.
- 몰린 회원은 진입부터 결제 시도까지 VU를 하나씩 잡는다. 몰림 시나리오의 `gracefulStop`은 관찰 시간 + 3분이라, 알림을 기다리는 회원이 관찰 시간 끝까지 갈 수 있다. 그래서 관찰 시간(`duration`)은 알림 대기 상한(8분)보다 길어야 한다.
- 대기 상한을 8분으로 둔 까닭: member는 알림 메시지를 태스크당 초당 약 20건 저장한다(동시 2건, 한 건 약 100ms. nova-infra member `application.yml`). 지금 1대라 5,000건이면 약 4분이 걸리고, 등록 큐가 비는 약 90초를 더하면 마지막 알림은 오픈 뒤 약 6분에 온다. 상한이 이보다 짧으면 줄 끝의 회원이 측정 도구 때문에 잘려 지연 분포의 끝이 보이지 않는다.
- 계획 계산은 결제할 회원이 입장 속도(초당 150)의 비율만큼 차례로 등록된다고 보고(초당 75 결제), 알림 수 확인은 결제할 회원 2,500명이 한꺼번에 기다리는 경우(초당 250건)로 크게 잡는다. 입장이 이어지는 약 30초 동안 앞쪽 회원의 결제가 이미 시작되므로 이 요청을 몰림 구간에 더한다.
- 판정은 spike처럼 본 시험 전체를 구간 하나(`rush`)로 본다. 대표 요청은 상품 목록, 대기열, 주문이다. 등록 알림이 하나도 오지 않으면 주문 요청이 없어 불합격이 된다.
- 결과에서 따로 볼 지표: `accept_to_notified`(접수부터 알림을 본 때까지), `open_to_payment`(판매 오픈부터 결제 시도 응답까지. 성공과 실패를 모두 센다), `rush_outcome`(`paid`, `left`, `notify_timeout`, `not_payable`, `order_failed`, `payment_failed`, `not_accepted`).

**stress**

- 단계마다 5분을 둔다. ECS 오토스케일(목표 60%, cooldown 60초)이 적어도 한 번은 반응할 수 있는 시간이다.
- 진입은 load와 같이 120/초에 묶는다. 입장 속도가 150/초로 고정되어 있어서, 진입을 더 올려도 접수 쪽 부하는 늘지 않고 VU만 늘어나기 때문이다. 접수 한계는 운영 설정을 바꾸는 시험(아래 "가설을 보는 곳")에서 본다.
- stress는 기준을 넘는 지점을 찾는 시험이므로 합격이나 불합격으로 판정하지 않는다. 결과로는 "기준을 지킨 마지막 단계"와 "처음 기준을 넘은 단계에서 먼저 막힌 곳"(서비스, DB 풀, Valkey)을 적는다. 중단 기준에 걸려 멈추는 것도 정상적인 결과이다. 그래서 stress는 마지막 단계까지 돌았거나 중단 기준으로 멈췄으면 워크플로가 성공하고, 지표가 끊긴 판정 불가일 때만 실패한다.

**soak**

- 4시간 동안 돌리면 풀 A 72,000명, 풀 C 14,400명, 풀 B 1,000명으로 모두 87,400명이 필요하다. 토큰 유효 시간은 4시간에 준비 시간과 30분을 더한 값이므로 상한(6시간 30분) 안에 들어간다.
- 시작할 때와 끝날 때의 값을 비교한다: 서비스 메모리, DB 커넥션 수, Valkey 메모리와 `wr:*` 키 수, preorder DB 행 수에 따른 조회 지연.
- 준비한 예약의 결제 기한은 등록 뒤 24시간이므로, 4시간 시험에서는 기한이 지나지 않는다.

**가설을 보는 곳**

| 가설(PLAN.md 목표 4) | 보는 시나리오 | 무엇으로 보나 |
|---|---|---|
| 이벤트 소비기가 건당 7.8ms 안에 처리하는가 | spike | 몰림 뒤에 `preorder-events`가 쌓이고 빠지는 속도. breakscale 02의 예측(등록 큐 최대 약 3,400건, 약 90초 뒤 모두 빠짐)과 비교한다 |
| worker 스케일 기준(`per_task: 50`)이 적절한가 | spike | worker가 몇 대까지 늘었는지(breakscale은 2대로 예측), 언제 늘었는지, 그때의 큐 길이 |
| 등록이 밀리면 결제가 얼마나 늦어지는가 | rush | `accept_to_notified`와 `open_to_payment`의 분포, `notify_timeout` 수. 등록 큐가 비는 시각(breakscale 02 예측 약 90초)과 알림이 몰리는 시각을 맞춰 본다 |
| 알림 저장이 판매 오픈을 따라가는가 | rush | `notification` 큐 길이와 `member.notifications.lag`. 태스크당 초당 약 20건이라는 추정이 맞으면 5,000건에 약 4분이 걸린다. member는 CPU로만 늘어나서 큐가 쌓여도 늘지 않을 수 있다 |
| 접수 한도 200/초의 원인 | 기본 시나리오로는 볼 수 없다 | 입장 속도가 150/초라서 접수가 200/초에 닿지 않는다. 입장 속도를 300/초로 올리는 breakscale 04, 05가 필요하다 |
| 등록 처리량과 Mock 지연의 관계 | 기본 시나리오에서는 지금 지연 값 한 점만 볼 수 있다 | 지연을 바꾸는 breakscale 06, 07이 필요하다 |

- 운영 설정을 바꿔야 하는 breakscale 시나리오는 k6만으로 재현할 수 없다. 이런 시험은 기본 시나리오를 마친 뒤 따로 승인받아 진행한다.
  - 04, 05: 입장 속도와 preorder 대수
  - 06, 07: Mock 지연과 실패율
  - 08: worker 대수 고정
- 11(재시도 폭주)은 나중에 k6 쪽 재시도 옵션으로 넣는다.

**흐름별 판정**

- 전체 요청의 80% 가까이가 상품 조회이므로, 전체 p95만 보면 예약이나 결제 쪽이 느려져도 드러나지 않는다. 그래서 전체 기준과 함께 `name`별로 0.5초 안에 끝난 비율과 5xx 비율을 낸다. 전체 기준과 흐름별 기준(진입·접수, 조회, 결제, 취소)을 모두 지켜야 합격이다.
- 대기열 확인(`GET /api/v1/preorders/queue`)의 응답 시간은 기준에 넣지만, 줄에서 기다린 시간은 넣지 않는다. 기다린 시간은 "진입부터 접수까지 걸린 시간" 지표로 따로 낸다.

## 토큰 발급

카카오 로그인은 자동화할 수 없다. 그래서 member의 서명키로 시험 회원의 토큰을 직접 만든다. 각 서비스는 서명, 클레임, 만료, 폐기 표시만 확인하므로, 직접 만든 토큰도 그대로 통과한다.

- 토큰 형식은 member가 만드는 토큰과 같다.
  - 헤더: `alg=RS256`, `typ=at+jwt`. `kid`에는 환경 변수 `JWT_KEY_ID`를 그대로 넣고, 개인키에서 계산하지 않는다
  - 클레임: `iss`와 `aud`는 환경 변수 `JWT_ISSUER`, `JWT_AUDIENCE`(지금 값은 `nova`, `nova-api`). `sub=<customers.id UUID>`. `sid`와 `jti`는 토큰마다 새 UUID. `role=USER`, `type=ACCESS`, `iat`, `exp`
  - 모든 클레임이 필수이고, 서비스는 `sid`도 검사한다.
- 시험 회원의 토큰은 폐기 확인(`auth:revoked-sid:{sid}`, `auth:nbf:{sub}`)에 걸리지 않는다. `sid`는 매번 새 값이고, 시험 회원은 로그인한 적이 없기 때문이다. 대기열(waitingroom)은 폐기 확인을 하지 않는다.
- `JWT_KEY_ID`, `JWT_ISSUER`, `JWT_AUDIENCE`는 인프라가 member 설정에서 읽어 발급기 작업 정의에 넣는다. 값을 한 곳에서 가져와야 member와 어긋나지 않는다. 셋 중 하나라도 비어 있으면 발급기는 토큰을 만들지 않고 실패한다.
- 서명키 비밀은 RSA 2048 개인키를 PKCS#8 PEM(`-----BEGIN PRIVATE KEY-----`)으로 담은 문자열 하나이다(JSON이 아니다). 작업 정의의 `secrets`가 이 값을 줄바꿈까지 그대로 환경 변수에 넣는다. 발급기는 PKCS#8 형식으로만 읽고, RSA가 아니거나 2048비트보다 작은 키면 실패한다.
- 발급기는 한 번 돌고 끝나는 ECS 태스크이다. 서명키 비밀은 이 태스크의 역할만 읽을 수 있고, AWS 밖으로 가져가지 않는다.
- 발급기는 일반 회원의 토큰만 만든다. `role=USER`는 코드에 고정하고 입력으로 받지 않는다. 시험 회원 ID 범위만 입력으로 받고, 범위 밖의 ID는 거절한다. 허용 범위는 실행할 때 받지 않고 이미지에 넣어 빌드한다. 실행 입력으로 받으면 누군가 범위를 넓혀 실제 회원의 토큰을 만들 수 있기 때문이다. 토큰의 유효 시간은 시험 시간에 30분을 더한 값이고, 최대 6시간 30분이다.
- 만든 토큰은 S3 `tokens/`에 둔다. 시험이 끝나면 컨트롤러가 바로 지우고, 컨트롤러가 죽었으면 워크플로의 뒷정리가 지운다. 접두사에 건 수명 주기(1일)는 남은 토큰을 치우는 안전망이다. 토큰을 읽을 수 있는 것은 k6 태스크뿐이다.
- 발급기 이미지는 셸이 없는 distroless 이미지에 실행 파일 하나만 둔다. 누군가 RunTask로 명령을 바꿔도 서명키를 꺼낼 방법이 없게 하려는 것이다.
- 발급기 이미지는 이 저장소 main 브랜치의 `build.yml`만 올릴 수 있다. main은 리뷰 필수로 보호하고, `token-minter/`, 허용 범위가 들어 있는 `config/`, 역할을 맡는 `.github/`에 CODEOWNERS를 둔다. 누군가 코드를 바꿔 관리자 토큰을 만드는 일을 막기 위해서이다.

## 저장소 보호

- `.github/workflows/`, 워크플로 규칙 검사(`tools/check-workflows/`), 그리고 `.github/CODEOWNERS` 자신을 CODEOWNERS에 넣는다. 워크플로를 바꾸면 OIDC로 맡는 역할을 다른 용도로 쓸 수 있고, CODEOWNERS를 바꾸면 리뷰 규칙을 풀 수 있기 때문이다.
- 브랜치 보호에서 "코드 소유자 리뷰 필수"를 켠다. 이 설정이 꺼져 있으면 CODEOWNERS는 리뷰어를 지정할 뿐 머지를 막지 못한다.
- `pull_request_target`은 쓰지 않는다. 이 이벤트는 fork에서 올린 PR에도 base 저장소의 권한과 비밀을 가지고 돈다. 공개 저장소에서는 누구나 PR을 올려 그 권한에 접근할 수 있다. 그래서 PR 검사는 `pull_request`로만 하고, `ci.yml`은 `permissions: contents: read`로 둔다. `ci.yml`의 워크플로 규칙 검사(`tools/check-workflows`)가 `pull_request_target`을 찾으면 실패한다. actionlint는 이 이벤트를 막지 않으므로 규칙 검사를 따로 둔다. 규칙 검사는 글자를 비교하지 않고 actionlint의 파서로 워크플로를 해석한 결과를 보므로, YAML 이스케이프(`"pull_request_\u0074arget"`)나 흐름 스타일(`- {uses: x@main}`)로 우회할 수 없다.
- **`loadtest` environment는 인프라 PR I-2(IAM)를 적용하기 전에 만든다.** 승인자를 지정하고, 배포 브랜치는 main만 허용한다. 워크플로가 없는 environment를 참조하면 GitHub가 보호 규칙 없이 environment를 새로 만들어 버린다. 그 상태에서 시험 실행 역할이 생기면, 쓰기 권한이 있는 사람은 누구나 아무 브랜치에서 승인 없이 그 역할을 맡을 수 있다. 같은 이유로 main 브랜치 보호도 I-2 전에 켠다(빌드 역할은 main 브랜치를 신뢰한다).

## 시험 데이터

### 준비

- **시험 회원**: be가 준 SQL로 `customers`에 미리 넣는다. 예약이 회원 행을 참조하므로, 행이 없으면 접수가 `MEMBER_NOT_FOUND`로 실패한다. 시험용임을 알아볼 수 있는 ID 규칙을 쓴다. 제안하는 규칙은 아래와 같고, 최종 규칙은 be와 정한다.
  - `id`: `10ad7e57-0000-7000-8000-<12자리 번호>`
  - `kakao_id`: `loadtest-<번호>`
- **시험 상품**: 시험마다 담당자가 관리자 화면에서 만든다. 발급기는 관리자 토큰을 만들 수 없으므로, 시험 상품을 자동으로 만들지 않는다.
  - 판매 방식은 선주문, 상태는 판매 중, 노출은 켬으로 두고, 옵션이 하나 이상 있어야 한다.
  - 회차의 `opensAt`은 시험 시작 전으로, `closesAt`은 시험이 끝난 뒤로 잡는다. 배송 차수도 넣는다.
  - 회차 일정이 대기열 서비스에 전달된 뒤에야 진입할 수 있다.

### 정리

시험 회원 ID 범위와 시험 상품 ID를 기준으로 지운다. 정리 SQL은 be에서 받는다.

- 시험이 끝나자마자 지우지 않는다. 시험이 끝나도 worker의 등록·취소와 `preorder-events` 소비는 SQS에서 한동안 이어진다. 처리 중인 예약을 지우면 소비하는 쪽에서 오류가 나고 메시지가 DLQ로 간다. 회차가 열려 있으면 실제 사용자가 진입할 수도 있다.
- 회차 마감은 관리자 API로만 할 수 있어서 컨트롤러가 할 수 없고, 마감했는지도 확인할 수 없다. 그래서 정리는 시험 실행과 떼어 `cleanup.yml`로 한다. 담당자가 runbook에 따라 회차를 마감하고 확인한 뒤, 시험 ID를 넣어 실행한다.
  - 정리 대상은 입력으로 받지 않고, 그 시험의 `results/<시험 ID>/plan.json`에서 읽는다. 대상은 진입에 쓴 상품(`product_id`), 준비에 쓴 상품(`prep_product_id`), 회원 범위이다. spike에서는 두 상품이 다르므로 둘 다 정리하고, 담당자도 두 상품의 회차를 모두 마감해야 한다. ID를 잘못 입력해서 다른 데이터를 지우는 일을 막기 위해서이다.
  - 컨트롤러를 정리 모드로 띄운다. 시험 클러스터에서 다른 시험의 태스크가 돌고 있으면 거절한다. 그 시험 때문에 큐가 비지 않기 때문이다.
  - 관련 큐가 빌 때까지 최대 30분 기다린다. SQS `GetQueueAttributes`의 `ApproximateNumberOfMessages`와 `...NotVisible`이 모두 0이면 빈 것으로 본다. CloudWatch 지표는 몇 분씩 늦게 나오므로 쓰지 않는다. 큐가 비면 정리 태스크를 돌리고, 30분 안에 비지 않으면 정리하지 않고 실패로 끝낸다. 그때는 나중에 다시 실행한다.
  - 결과는 `results/<시험 ID>/cleanup.json`에 남긴다. 정리 태스크(인프라 I-6)가 생기기 전에는 runbook에 따라 손으로 지운다.

| 위치 | 지우는 대상 |
|---|---|
| preorder | `preorders`, `preorder_events`, `preorder_sync_jobs`, `preorder_sync_attempts`, `preorder_outbox_events`, `preorder_dead_letter_events`, 시험 상품의 회차와 배송 차수 |
| order | `orders`, `order_items`, `order_events`, `order_outbox_events` |
| payment | `payments`, `payment_transactions`, `payment_outbox_events` |
| 그 밖 | `notifications`, 시험 상품(catalog) |
| Valkey | `wr:*:{시험 상품 ID}` |
| Mock | `external_mock.preorder_registrations`에 남은 시험 건 |

- 회원 행은 계속 쓰므로 시험마다 지우지 않는다.

## 인프라 값

- 작업 정의는 패밀리 이름으로 받아서 최신 개정판을 띄운다. 이미지는 `latest`를 쓴다. RunTask로는 이미지를 바꿀 수 없으므로 결과에 이미지 다이제스트와 커밋을 남긴다.
  - 시험 도중에 `build.yml`이 `latest`를 바꾸면, RunTask를 여러 번 나눠 부르는 사이에 k6 이미지가 섞일 수 있다. `build.yml`을 `loadtest`와 같은 동시 실행 그룹에 넣는 방법은 쓰지 않는다. 한 그룹에서 기다릴 수 있는 실행은 하나뿐이라서, 기다리던 빌드나 시험이 뒤에 온 실행에 밀려 알림 없이 취소되기 때문이다.
  - 대신 `build.yml`은 커밋 해시 태그를 먼저 올리고, 시험 클러스터에 RUNNING 태스크가 없을 때만 `latest`를 옮긴다. 시험 중이면 `latest`를 옮기지 않고 실패하며, 시험이 끝난 뒤 다시 실행한다.
  - 이렇게 해도 확인한 시점과 시험이 시작되는 시점 사이에 짧은 틈이 남는다. 그래서 컨트롤러가 시작 시각 전에 `DescribeTasks`로 컨테이너의 `imageDigest`를 비교하고, 다르면 부하를 보내기 전에 시험을 취소한다. 시험이 끝난 뒤에 결과를 버리는 것보다 낫다.
- k6는 public 서브넷에서 공인 IP로 돌고, 컨트롤러와 발급기는 app 서브넷에서 돈다. public 서브넷은 공인 IP를 자동으로 주지 않으므로 k6는 `assignPublicIp=ENABLED`로 띄운다.
- 관측(obs) 서비스는 `awsvpc` 모드라서 다시 뜰 때마다 IP가 바뀐다. 그래서 고정 IP를 받지 않고, 컨트롤러가 Mimir를 서비스 이름으로 찾는다.
  1. `ListTasks(cluster, serviceName, desiredStatus=RUNNING)`로 obs 태스크를 찾는다.
  2. `DescribeTasks`로 ENI의 `privateIPv4Address`를 얻는다. 재배포 중에는 태스크가 잠시 두 개일 수 있으며, 그때는 가장 늦게 시작한(`startedAt`) 태스크를 쓴다.
  3. `http://<IP>:<port><queryPath>`로 조회한다. 조회가 실패하면 IP를 다시 찾는다.
  - 판정 쿼리는 모두 즉시 쿼리(`/api/v1/query`)로 보낸다. 지난 구간(유지 구간, stress의 각 단계)은 `time` 인자에 구간의 끝 시각을 주고, 범위를 구간 길이로 잡는다. 구간 누락도 `count_over_time` 같은 즉시 쿼리로 확인한다. 그래서 인프라가 준 `queryPath` 하나로 충분하다.
- **SSM 파라미터 두 개**(`run-task`, `observability`. 둘 다 String이고 값은 JSON 하나)는 워크플로의 `run` 작업이 읽어서 컨트롤러 RunTask의 환경 변수로 넘긴다. 컨트롤러는 SSM을 직접 읽지 않는다. 값을 워크플로 한 곳에서만 읽으므로 컨트롤러 역할에 SSM 권한이 필요 없고, 시험마다 어떤 값으로 돌았는지가 결과(`plan.json`)에 함께 남는다.
  - 컨트롤러는 시작하자마자 두 값의 필수 항목과 형식을 검사한다. 항목이 빠졌거나 형식이 틀리면 발급기나 k6를 띄우기 전에 실패한다.
  - 공개 저장소의 Actions 로그는 누구나 볼 수 있다. 그래서 워크플로는 읽은 값을 출력하지 않고, 읽은 직후에 `::add-mask::`로 가린다. 여러 줄 JSON을 통째로 가리면 줄 단위로만 가려지고, 버킷 이름처럼 값의 일부가 따로 찍힐 때는 가려지지 않는다. 그래서 JSON의 값을 하나씩 가린다.
  - 가리지 않을 키를 정해 두고, 나머지는 모두 가린다. 가리지 않는 키는 이 저장소 문서에 이미 공개된 이름이다: `cluster`, `taskDefinition`, `container`, `assignPublicIp`, `otlpEndpoint`, `mimir.cluster`, `mimir.service`, `mimir.port`, `mimir.queryPath`. 이런 값까지 가리면 `nova-prod-loadtest-github-run` 같은 역할 이름도 `***-github-run`으로 바뀌어 로그를 읽을 수 없다. 결국 가리는 값은 버킷 이름, 서브넷 ID, 보안 그룹 ID이고, 인프라가 나중에 더하는 키도 기본으로 가린다.
  - `run-task`의 `tasks`에는 지금 `controller`, `tokenMinter`, `k6`만 있다. 준비·정리 태스크(인프라 I-6)가 생기면 인프라가 같은 형식으로 `data`를 더한다. 그전에 `cleanup.yml`을 실행하면 컨트롤러를 띄우기 전에 거절한다.
- **k6의 지표 수집 주소는 컨트롤러가 덮어쓴다.** 컨트롤러는 k6를 띄울 때 `observability`의 수집 주소를 `K6_OTEL_HTTP_EXPORTER_ENDPOINT`로 넘긴다. 작업 정의나 이미지에 다른 값이 있어도 RunTask의 덮어쓰기가 우선한다. k6는 `K6_OTEL_*`를 표준 `OTEL_*` 변수보다 먼저 보므로, `OTEL_EXPORTER_OTLP_ENDPOINT`로는 주소를 바꿀 수 없다.
  - 수집 주소(`otlpEndpoint`)는 scheme이 없는 `host:port` 형식으로 온다. 이 값을 그대로 `K6_OTEL_HTTP_EXPORTER_ENDPOINT`에 넣고, 경로는 k6 기본값인 `/v1/metrics`를 쓴다.
  - 시험마다 같은 OTel 설정(`K6_OTEL_EXPORTER_PROTOCOL=http/protobuf`, `K6_OTEL_HTTP_EXPORTER_INSECURE=true`, `K6_OTEL_SERVICE_NAME`, `K6_OTEL_METRIC_PREFIX`)은 인프라가 k6 작업 정의에 고정값으로 넣는다. k6의 기본 전송 방식은 gRPC이므로, 이 값이 빠지면 4318 포트로 보내지 못한다. 컨트롤러는 수집 주소와 태스크마다 다른 값(`OTEL_RESOURCE_ATTRIBUTES` 등)만 넣는다. 값마다 정하는 곳을 한 곳으로 두려는 것이다.
  - 고정값은 `K6_OTEL_SERVICE_NAME=k6`, `K6_OTEL_METRIC_PREFIX=k6_`이다. Mimir는 여기에 단위와 종류를 나타내는 접미사를 더 붙인다(예: `k6_http_reqs_total`, `k6_http_req_duration_milliseconds_bucket`). `job` 라벨은 `loadtest/k6`이다. 최종 지표 이름은 smoke(C-2)에서 확정한다.
  - 직접 만드는 Trend(`entry_to_accept`)는 `new Trend('entry_to_accept', true)`로 만들어 시간 값임을 밝힌다. 그래야 단위가 ms로 나가서 `http_req_duration`과 같은 버킷 경계와 이름 규칙을 따른다.
- 태스크마다 `OTEL_RESOURCE_ATTRIBUTES=service.instance.id=<태스크 번호>,service.namespace=loadtest`를 넣는다. `service.instance.id`가 없으면 여러 태스크의 지표가 한 시계열로 섞인다. 게이트웨이의 리소스 속성 허용 목록에는 두 값이 모두 들어 있다.
- k6의 `systemTags`는 `status, method, name, scenario, expected_response`만 쓴다. 지표가 운영과 같은 Mimir에 쌓이므로, 시험 하나의 시계열을 2만 개 안으로 유지해야 한다.
  - Mimir의 한도는 시계열 150,000개, 초당 수집 10,000건이고, 운영 지표와 함께 쓴다.
  - 히스토그램 하나는 `name` × `status` 조합마다 시계열 18개를 만든다(경계 15개에 `+Inf`를 더한 버킷 16개, 합계, 개수). 요청 이름이 12개쯤이므로 태스크 하나에 수백~1,300개가 생긴다. 태스크마다 따로 쌓이므로 이 값에 태스크 대수를 곱해야 한다. 입력 확인 단계에서 이 값을 계산하고, 2만 개를 넘으면 멈춘다.
  - 게이트웨이에서는 필요한 k6 지표만 통과시킨다. 다만 이것은 안전망이고, 시계열 수는 k6 쪽의 `tags.name`과 `systemTags`로 지킨다. 통과시키는 지표는 `http_req_duration`, `http_reqs`, `http_req_failed`, `iterations`, `dropped_iterations`, `vus`, 진입부터 접수까지 걸린 시간(`entry_to_accept`, 히스토그램), 오류 코드 카운터(`error_code` 태그)이다. 오류 코드 값은 be의 오류 코드 목록 안에서만 나오므로 시계열이 늘지 않는다.
- 시험 클러스터는 실행기 CPU를 보기 위해 Container Insights를 켠다.
