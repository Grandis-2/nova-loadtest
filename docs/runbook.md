> 초안이다(NV-658). C-2(상품 조회 smoke)를 2026-10-19에 돌렸고, C-4(전체 smoke)를 돌리면서 대시보드 이름과 손 정리 절차를 채운다. "C-4에서 채운다"로 표시한 곳이 그 자리다.

- 공개 저장소다. 이 문서와 실행 기록에 부하 시험 헤더 값, 토큰, 계정 ID가 들어간 ARN, 시험 회원 목록을 적지 않는다.
- 운영에 부하를 보내는 실행은 매번 담당자 승인을 받는다. 처음에는 smoke(초당 5건)로 시작한다.

## 실행 전 점검표

러너는 회차 일정, 경보, DB를 볼 수 없다. 승인자는 아래 항목을 확인한 뒤에 승인한다. 상품 조회만 하는 smoke(`flows=catalog`)는 회원과 시험 상품을 쓰지 않으므로 "시험 상품"과 "시험 회원"을 건너뛴다.

### 이미지와 클러스터

- [ ] main의 `build.yml` 마지막 실행이 성공했다(`latest`가 main을 가리킨다). 실패했으면 [build.yml 이 실패했을 때](#buildyml-이-실패했을-때)를 본다
- [ ] 다른 시험이 돌고 있지 않다. Actions의 `loadtest` 실행 목록에 진행 중인 실행이 없다

### 시험 상품

시험마다 새 시험 상품을 쓴다. spike는 진입할 상품(`product_id`)과 준비에 쓸 상품(`prep_product_id`) 두 개가 필요하다. rush는 상품 하나만 쓰고, 그 회차가 열리는 시각을 `open_at`으로 넣는다.

`cmd/testproduct`로 만든다. 담당자가 자기 관리자 세션으로 직접 돌리고, 관리자 토큰은 저장소, 워크플로, AWS 어디에도 남지 않는다.

```sh
read -rs NOVA_ADMIN_TOKEN && export NOVA_ADMIN_TOKEN   # 관리자 화면에 로그인한 세션의 토큰
go run ./controller/cmd/testproduct -dry-run           # 보낼 본문 확인
go run ./controller/cmd/testproduct                    # smoke, load, stress, soak: 상품 하나
go run ./controller/cmd/testproduct -spike             # spike: 준비 상품과 진입 상품
go run ./controller/cmd/testproduct -rush              # rush: 상품 하나, 회차가 열리기 전에 실행
unset NOVA_ADMIN_TOKEN
```

- 명령은 사전예약 상품(공개, 옵션 두 개, 배송 차수 하나)을 등록하고, preorder가 회차를 만들 때까지 기다린 뒤, 공개 상세가 판매 중인지 확인한다. 마지막에 `loadtest.yml`에 넣을 값과 실행해도 되는 시각을 출력한다.
- be는 회차를 **지금부터 30분 뒤**부터 열 수 있게 한다. 그래서 시험 30분 이상 전에 만든다. 기본 오픈은 지금 + 31분 남짓, 회차 길이는 12시간(`-length`)이다.
- spike는 준비 상품을 먼저 열고, 진입 상품은 그 30분 뒤(`-open-at`)에 연다. 준비 상품이 열린 뒤, 진입 상품 오픈 15분 전까지 실행한다. `-open-at`을 준비 상품 오픈 15분 안으로 주면 거절하고, 75분보다 멀게 주면 `open_at`이 1시간 안에 들도록 출력하는 실행 시작 시각을 늦춘다.
- rush는 회차가 열리기 전에 실행한다. 상품을 만든 뒤, 회차 오픈 15분 전까지 실행한다(토큰 5,000개 발급과 k6 기동이 그 사이에 든다).
- 비공개 상품은 대기열이 줄을 열지 않으므로 공개로 만든다. 이름이 `[부하 시험]`으로 시작해 실제 사용자도 시험 상품임을 알 수 있다.
- 중간에 실패해도 이미 만든 상품은 남는다. 출력된 상품 ID와 `Idempotency-Key`로 관리자 화면에서 마감한다.

명령을 쓰지 않고 관리자 화면에서 직접 만들 때는 아래를 확인한다. 명령으로 만들었으면 앞의 다섯 항목은 이미 맞다.

- [ ] 판매 방식 선주문, 상태 판매 중, 노출 켬
- [ ] 옵션이 하나 이상 있고 판매 중이다
- [ ] 회차의 `opensAt`이 시험 시작 전이다. spike의 진입 상품과 rush의 상품은 `open_at`(본 시험 시작 시각)으로 둔다
- [ ] 회차의 `closesAt`이 시험 예상 종료 시각보다 뒤다(계획 표의 "예상 시간")
- [ ] 배송 차수가 있다
- [ ] 회차 일정이 대기열 서비스에 전달됐다(C-4에서 확인 방법을 채운다)

### 시험 회원(DB)

- [ ] 시험 회원이 들어가 있다. 준비 SQL을 돌린 기록이 [실행 기록](#실행-기록)이나 be 쪽 기록에 있다(2026-10 기준 10만 명)
- [ ] 계획 표의 "필요 회원"이 시험 회원 수보다 적다(넘으면 `plan` 작업이 멈춘다)

### 경보(Grafana)

- [ ] 지금 울리는 경보가 없다. 울리는 중이면 시험하지 않는다(시험이 원인을 가린다)
- [ ] 사일런스를 걸었다
  - 대상: `nova-slo` 그룹(`slo-*`, `traffic-drop`, `latency-vs-baseline`), `nova-http-p99`, `nova-http-5xx`
  - 끝 시각: 계획 표의 예상 종료 시각 + 15분
  - 설명(comment)에 시험 ID를 적는다(시험 ID는 `plan` 작업의 출력에 있다)

### 일정

- [ ] 운영 배포, DB 작업, 다른 부하 작업과 겹치지 않는다
- [ ] 시험 시간 동안 결과를 지켜볼 사람이 있다

## 실행

### 입력

Actions → `loadtest` → Run workflow(브랜치 main). 입력은 [설정과 비밀 값](configuration.md#워크플로가-러너-명령cmdgha에-넘기는-값)에도 있다.

| 입력 | 내용 | 비우면 |
|---|---|---|
| `scenario` | `smoke`, `load`, `spike`, `rush`, `stress`, `soak` | `smoke` |
| `product_id` | 진입할 시험 상품 ID(필수) | |
| `prep_product_id` | 준비 구간 상품. spike는 필수, rush는 비운다 | `product_id` |
| `open_at` | 판매가 열리는 시각(RFC3339). spike와 rush만(필수) | |
| `peak_rps` | 흐름 시작 수 합계(초당) | 시나리오 기본값 |
| `duration`, `ramp_up` | 유지 시간, 올리는 시간(예 `10m`) | 시나리오 기본값 |
| `runners` | k6 태스크 대수. 계산한 값보다 적으면 멈춘다 | 계산한 값 |
| `flows` | 돌릴 흐름(쉼표로 구분). 상품 조회만: `catalog` | 시나리오 기본값 |
| `abort_error_rate` | 중단할 오류율(%) | 5 |

명령줄로도 실행할 수 있다.

```sh
gh workflow run loadtest.yml --ref main \
  -f scenario=smoke -f product_id=<시험 상품 ID> -f flows=catalog -f duration=2m
```

### 계획 표 확인

`plan` 작업이 끝나면 실행 요약에 계획 표가 나온다. 승인하기 전에 본다.

- 흐름별 도착률, 태스크 대수, 필요 회원, 최대 VU, 예상 시계열 수, 예상 시간이 입력한 의도와 맞는지
- 경고(`::warning::`)가 있는지
- 계획이 틀렸으면 승인하지 않고 실행을 취소한다(아직 아무것도 띄우지 않았다)

### 승인

`run` 작업은 environment `loadtest`의 승인을 기다린다. 승인자가 [실행 전 점검표](#실행-전-점검표)를 확인한 뒤 Review deployments → Approve 한다. 승인은 한 번이고, 사전 점검부터 뒷정리까지 한 작업으로 돈다.

- `concurrency: loadtest` 때문에 같은 시간에는 시험이 하나만 돈다. 시험이 도는 동안 두 번 넘게 실행하면 앞서 기다리던 실행이 알림 없이 취소된다. 기다리는 실행은 하나만 둔다.

## 지켜보기

- **실행 로그**: `run` 작업의 로그에 컨트롤러 로그가 `[controller]`로 옮겨진다. 토큰 발급, k6 태스크 띄우기, 시작 시각(`START_AT`), 감시, 판정 순서로 나온다
- **Grafana**: 시험 대시보드(C-4에서 이름을 채운다)에서 시험 ID로 거른다. 서비스 쪽은 평소 보는 대시보드에서 지연, 5xx, 대기열 길이를 본다
- 컨트롤러가 스스로 멈추는 경우
  - 오류율이나 5xx 비율이 `abort_error_rate`를 1분 넘게 넘으면 "중단"
  - k6 태스크 하나의 지표가 1분 넘게 들어오지 않거나 Mimir를 1분 넘게 조회하지 못하면 "판정 불가"
  - 시작 시각까지 태스크가 모두 RUNNING이 되지 않거나 이미지가 섞이면 "취소"

## 멈추기

| 상황 | 방법 | 결과 |
|---|---|---|
| 서비스가 위험하다, 부하를 바로 내려야 한다 | Actions → `stop` → `test_id` 입력. 승인 없이 바로 돈다 | k6 태스크가 멈추고 컨트롤러가 "중단" 결과를 쓴다. `loadtest` 실행은 실패로 끝난다 |
| 토큰 발급 중(k6 를 띄우기 전)에 멈춘다 | 위와 같다 | 컨트롤러와 발급기를 멈춰 k6 가 뜨지 않는다. 결과가 남지 않아 "판정 불가"로 끝난다 |
| 워크플로를 그만 돌린다 | `loadtest` 실행 취소 | 뒷정리 단계(`if: always()`)가 태스크를 멈추고 토큰을 지운다. GitHub에서 이 동작을 C-4에서 확인한다(로컬 Forgejo는 취소하면 뒷정리를 돌리지 않는다) |
| 위가 모두 안 된다 | 콘솔 ECS → 클러스터 `nova-prod-loadtest` → 태스크에서 시작자(`startedBy`)가 시험 ID인 태스크를 모두 중지 | 컨트롤러까지 멈추면 결과가 남지 않는다 |

- `stop`의 `test_id`는 `plan` 작업의 출력, 실행 로그, Slack 알림에 있다. 형식은 `lt-<yyyymmdd>t<hhmm>-<번호>`이다.
- 멈춘 뒤에도 [끝난 뒤](#끝난-뒤)의 사일런스 해제와 정리를 한다.

## 결과 읽기

결과는 실행 요약, Slack, S3 `results/<시험 ID>/summary.json`(`summary.md`)에 있다.

| 결과 | 뜻 | 워크플로 | 다음 할 일 |
|---|---|---|---|
| 합격(`pass`) | 판정 구간마다 기준을 지켰다 | 성공 | 실행 기록에 남긴다 |
| 불합격(`fail`) | 끝까지 돌았지만 기준을 넘었다 | 실패 | 흐름별 표에서 걸린 요청을 보고 서비스 쪽 원인을 찾는다 |
| 한계 측정(`limit`) | stress. 기준을 지킨 마지막 단계를 적는다 | 성공 | 마지막 합격 단계를 기록한다 |
| 중단(`aborted`) | 중단 기준, k6 임계치(99), `stop`으로 멈췄다 | 실패 | 까닭(reason)을 본다. 서비스 문제면 원인을 찾고, 다시 돌리기 전에 승인을 다시 받는다 |
| 판정 불가(`inconclusive`) | 지표가 끊겼거나 Mimir 를 조회하지 못했거나, 컨트롤러가 결과 없이 끝났다 | 실패 | [판정 불가일 때](#판정-불가일-때)를 본다 |
| 취소(`canceled`) | 부하를 보내기 전에 멈췄다 | 실패 | 까닭을 고치고 다시 돌린다. 부하가 가지 않았으므로 사일런스만 확인한다 |

## 끝난 뒤

1. **사일런스 해제**: 끝 시각 전에 끝났으면 사일런스를 직접 푼다.
2. **회차 마감**(회원 흐름을 돌린 시험만): 관리자 화면에서 시험 상품의 회차를 마감한다. spike는 두 상품을 모두 마감한다. 마감됐는지 화면에서 다시 확인한다.
3. **정리**: 회차를 마감한 뒤에 한다. 바로 지우지 않는다(worker 가 SQS 메시지를 아직 처리하고 있을 수 있다).
   - 정리 태스크(인프라 I-6)가 생긴 뒤: Actions → `cleanup` → `test_id` 입력 → 승인. 컨트롤러가 관련 큐가 빌 때까지(최대 30분) 기다렸다가 정리 태스크를 돌리고 `results/<시험 ID>/cleanup.json`을 남긴다. 다른 시험이 돌거나 끝나지 않은 시험이면 거절한다
   - 정리 태스크가 생기기 전: be 에서 받은 정리 SQL 을 손으로 돌린다(C-4에서 절차를 채운다). 대상은 `results/<시험 ID>/plan.json`의 상품 ID 와 회원 범위다. 입력한 ID 가 아니라 이 파일의 값을 쓴다
4. **실행 기록**: 아래 표에 한 줄 남긴다.

## 문제 해결

### 판정 불가일 때

| 까닭(reason) | 먼저 볼 것 |
|---|---|
| 컨트롤러가 결과(summary.json) 없이 끝났다 | `run` 작업 로그의 `[controller]` 줄. 컨트롤러 태스크가 죽었으면 뒷정리가 k6 를 멈췄는지 ECS 에서 확인한다 |
| k6 태스크 N의 지표가 1분 넘게 들어오지 않았다 | k6 태스크 로그의 내보내기 오류. 수집 주소(SSM `observability`의 `otlpEndpoint`)와 게이트웨이 상태 |
| Mimir 를 1분 넘게 조회하지 못했다 | 관측 클러스터의 Mimir 태스크. 재배포 중이었는지 |
| 구간 X에서 k6 태스크 N의 지표가 빠졌다 | 그 시간의 게이트웨이, Mimir 수집 상태 |

### build.yml 이 실패했을 때

- `idle check`에서 실패: 시험이 돌고 있어 `latest`를 옮기지 않았다. 시험이 끝난 뒤 `build` 를 다시 돌린다(Run workflow).
- `main head`에서 실패: 그 사이 main 에 새 커밋이 들어왔다. 새 커밋의 `build` 가 `latest`를 옮긴다.
- `move latest`에서 "옮기는 동안 시험이 시작됐다": 그 시험을 `stop`으로 멈추고 다시 돌린다(컨트롤러와 k6 이미지가 다를 수 있다).

### 불합격일 때

- 실행 요약의 구간별 표에서 기준(0.5초 안 95%, 5xx 0.1%)에 못 미친 요청 이름을 찾는다. 전체가 합격이어도 이름 하나가 걸리면 불합격이다.
- 그 요청을 처리하는 서비스의 지연과 DB 지표를 같은 시간대로 본다. 부하가 작은데도 걸렸다면 부하가 아니라 서비스 쪽(쿼리, 캐시)의 문제일 가능성이 크다.
- 원인을 고치기 전에는 같은 시험을 되풀이하지 않는다. 고친 뒤 같은 입력으로 다시 돌려 비교한다.

### 실행 전에 멈췄을 때

- `plan` 작업 실패: 입력이 상한을 넘었거나, 회원이 모자라거나, 시계열이 2만 개를 넘었다. 오류 메시지대로 입력을 고친다.
- `run` 작업의 사전 점검 실패: 시험 상품이 없거나, 판매 중이 아니거나, 판매 중인 옵션이 없다. 관리자 화면에서 고친다.
